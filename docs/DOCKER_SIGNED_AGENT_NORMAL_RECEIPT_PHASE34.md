# Docker Phase 34 — one evidence standard for normal and replayed signed receipts

After merged PR #669, `--resend-receipt` checked the full stable, owner-private recovery inventory before signing its saved terminal outcome and again before recording receipt acknowledgement. But **the normal `--execute-lab` path still skipped those checks**: it released its agent lock immediately after the container's terminal event, then sent a signed receipt and appended `receipt_accepted` without checking the full journal history. Also, the receipt-only `alreadyAcknowledged:true` shortcut read just one file and did not reconcile its complete local history.

This phase unifies them. It changes the **actual signed-agent path** in `scripts/docker-lab-agent.mjs`, adds a pure post-acknowledgement evidence gate, tests and runbook. No Docker daemon, cloud dispatch, host approval or production opt-in is enabled in CI.

## Six related improvements

1. **Strict pre-send admission on normal dispatch.** After recording `completed` or pre-attempt `guard_denied` durably and releasing the exact original container lock, keep the agent lock held while running the existing Phase 33 `requireSignedReceiptReplayClear(auditSignedAgentRecoveryDirectory(), {phase:"before_send"})` gate. Demand the original claim UUID, agent UUID, full container ID, outcome, owner-private directory, canonical history and no unresolved same-target attempts, legacy `failed`, or retained target locks. Do not sign a receipt based on one terminal event alone.
2. **Second inventory after network acknowledgement.** Validate the server's signed agent report acknowledgement, re-audit all recovery files and require the original claim's SHA-256, target and outcome to be unchanged before appending `receipt_accepted`. The remote reply is not an independent Docker event attestation.
3. **Durable accepted-state proof before success.** After fsyncing the acknowledgement, `requireSignedReceiptAcknowledgedEvidence()` accepts only the canonical `reserved → attempted → completed → receipt_accepted` or `reserved → guard_denied → receipt_accepted`, paired with one original agent lock, no remaining container lock and no unresolved same-target history. A prior `failed` record cannot become a proven completion, even if it was previously acknowledged.
4. **Safe failure disposition and recovery locks.** If pre-send evidence fails, retain the agent lock for human review. If a network request times out or its reply is lost, and a **fresh full read-only inventory still proves that the same original terminal file is unchanged**, release only the agent lock so a human operator may deliberately use Docker-free `--resend-receipt`. A mismatch, tamper, crash or failed durability check retains that lock. Never re-execute a Docker operation.
5. **Already-acknowledged shortcut must be truthful.** The receipt-only mode can print `alreadyAcknowledged:true` only if the exact canonical acknowledged claim passes a complete owner-private inventory check. This path makes **no network calls and no Docker calls**, but it cannot silently endorse corrupted or conflicting legacy receipts.
6. **Cross-phase offline regression suite.** Verify the same fsynced local journal transitions as the real agent, missing original locks, retained container locks, old UNKNOWN/failed records, wrong identities/outcomes, symlinks, unreadable permissions, mutable claims, unrelated target isolation and precise normal-vs-replay source call ordering. Dedicated GitHub CI additionally runs earlier Phase 26–33 safety tests.

## Recovery operator procedure

Use `node scripts/docker-lab-recovery.mjs --strict-inventory` to inspect, **not clear**, recovery evidence. For a terminal but unacknowledged result, `--resend-receipt CLAIM_UUID` may replay the *original* signed `completed` or `guard_denied` report only after the normal complete-history admission gate. A previous UNKNOWN or legacy `failed` is **not** eligible. For missing or conflicting local evidence, leave the locks in place for independent human review.

### Strict boundaries

This implementation protects one operator-owned, local journal filesystem. It does not detect privileged changes by a different host, an unrelated Docker CLI, malicious operator-account processes or storage that violates `fsync` guarantees. The original Ed25519 permit, pinned rootless Engine, Phase 29 last-moment check, Phase 30 target lock, Phase 31 history fence, Phase 32 durable journals and Phase 33 manual replay gate remain intact. **No production execution is certified or enabled**. Successful network acknowledgement is still only a signed agent claim, not proof of physical execution.
