# Education — protected hosted staging atomic finalization

**Status: source only; NOT DEPLOYED. This PR does not run any hosted grading workflow, activate production, provision infrastructure, incur AI/GPU costs or modify any real student grade.**

After the controlled synthetic student exam (#388) and instructor review (#394), this closes the *last source-level operational gap* between a reviewed written response and an **official ledger-backed student grade**: a manual, separately authorized staging service-only finalizer and independent evidence.

## Three-stage operator path

**Preflight (default, read-only)** signs in two separate synthetic students and the approved synthetic instructor through real Supabase Auth. It verifies three different real JWT identities, continuing instructor grant, non-admin authority, owner-only submitted attempt, a genuine written answer, the exact persisted instructor review mark, and that the student's official grade is still pending. Both other student and anonymous callers are denied the official result and direct grade ledger. **No privileged key is injected; no Education write RPC is called.**

**Finalize (manual, irreversible write)** requires independently checking *both* workflow flags, one for official synthetic grading and one acknowledging the official score becomes immutable. The protected GitHub environment must also approve. The same preflight runs **before** the trusted key is used. Only then does the process call the already-reviewed atomic database function `education_finalize_cbt_grade(p_attempt_id)` through the **staging-only service-role key**, for exactly the reviewed synthetic attempt. The return must indicate `finalized`, zero outstanding human reviews and the *independently specified* exact score/max. Student A's own receipt must immediately match. One idempotent replay must return `already_finalized` with the same marks; the runner never regrades directly or updates tables.

**Verify (read-only)** runs only after finalization, using the two students and instructor with the **publishable key only**. It independently proves a valid five-field final receipt and timestamp, stable repeated reads, exact attempt grade, written answer's reviewed points without fabricated objective correctness, other-student/anonymous denial and no raw ledger SELECT privilege. **No service-role key is provided in verify mode.**

## Required independent setup and safety controls

1. Use a **separate synthetic Supabase staging project**, never live production or actual learners. The configuration inherits the known-production SHA-256 fingerprint block, exact HTTPS Supabase project hostname, distinct production/staging refs and dedicated synthetic `rls-` email/password requirements from existing staging workflows.
2. Apply all reviewed Education SQL scripts to staging via a **separate approved deployment**, including verified instructor grants, review queue, atomic grade ledger and verified-student-result RPC. This PR does not apply SQL or change production. Confirm that the published exam is active, Student A is enrolled, the attempt is submitted, and the written response has already been reviewed by the currently approved owning instructor.
3. Configure the same protected `rls-staging` GitHub environment with a required reviewer; retain the existing Student A/B and instructor staging secrets. Add the separate **staging-only service-role key** as protected secret `ETERNYX_EDU_STAGING_SERVICE_ROLE_KEY`. Prefer a short-lived staging-only credential, not a production credential. Modern `sb_secret_` keys are accepted only in the explicitly authorized mode; a legacy signed JWT must carry `role=service_role` and the **exact** staging project ref. Do not paste any secret into chat, a commit, a PR description or a log.
4. Configure these protected environment **variables** from independently reviewed synthetic data: `ETERNYX_EDU_REVIEW_TEST_ID`, `ETERNYX_EDU_REVIEW_ATTEMPT_ID`, `ETERNYX_EDU_REVIEW_ANSWER_ID`, `ETERNYX_EDU_REVIEW_AWARDED_POINTS`, `ETERNYX_EDU_FINALIZE_EXPECTED_SCORE`, and `ETERNYX_EDU_FINALIZE_EXPECTED_MAX`. The test/attempt/answer IDs must be distinct valid UUIDs. Point totals must be integers, nonnegative, and no greater than the expected maximum; maximum must be positive. The operator should derive expectations from the **trusted authored bank and reviewed answer**, not from a browser's submitted score.
5. Manually run `ETERNYX Education trusted staging final-grade acceptance` in **preflight** (default) mode with approval checkboxes **off**. Inspect the fixed 18-case sanitized evidence and separately check staging snapshot/backup readiness.
6. Only after a clean preflight, deliberately select **finalize** and tick **both** `approve_one_official_grade` and `acknowledge_immutable_grade`. The protected environment reviewer must approve the run. This performs a persistent official-grade change to **one** staging synthetic attempt. The finalizer never performs direct SQL writes or deletes and does **not** automatically clean up the fixture.
7. Run **verify** with no write approvals and confirm all 21 read-only cases. Only the finalization run has access to the privileged key. If a finalize HTTP request fails, **do not blindly retry**: the database transaction might have committed. Inspect the staging record and student receipt using approved access, then decide whether a fresh preflight or a read-only verify is appropriate. Reuse of an already finalized fixture will intentionally fail the preflight.
8. Review, document and rotate synthetic fixtures manually as needed. This workflow never resets a grade, changes a user's official mark or deletes a test. Keep production flags off until separately approved migration, backup/rollback, frontend and real hosted release acceptance.

## Evidence and limitations

Mode-specific sanitized evidence counts are **18 preflight**, **28 finalize**, and **21 verify** checks. Each artifact contains only fixed scenario labels, pass/fail, mode and operational safety booleans. An independent offline validator rejects unexpected fields, partial cases, secret identifiers, false production claims, hidden service-role invocations and missing Auth sign-out. Evidence is retained for seven days.

A successful staged finalizer run would establish a concrete verified synthetic grading flow, but **it would not certify production migration safety, row-level security in a different project, the full live UI, billing, backups, timeouts or workflow scheduling**. Staging hosting may have ordinary Supabase quota/plan charges if the operator separately chooses to use a hosted staging project. This source change does not provision one.

This is a reviewable implementation of a real feature, not decorative scoring cards or a promise that an unrun staging check has already passed.
