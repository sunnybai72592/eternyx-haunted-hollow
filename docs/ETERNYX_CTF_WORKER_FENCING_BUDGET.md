# ETERNYX Cyber Range — Worker Fencing and Zero-Default Resource Budgets

## Scope and activation

**This is a local operator / staging control-plane milestone, not a production public range.** No resources, background workers, paid cloud VMs or ingress endpoints are enabled by merging this PR. The existing vulnerable training target remains developer-local. All newly introduced daily budgets default to **zero**.

### Eight delivered improvements

1. **Server-trusted worker identity:** `CTF_RANGE_PROVIDER_ID` is set in the trusted Edge Function environment, never in the user's JSON request. An independent purpose-scoped worker API secret is still required.
2. **Single-owner coordinator leases:** SQL `ctf_range_worker_acquire` grants one 180-second worker-generation UUID per provider. Only a matching owner and UUID can renew while it is live; a different owner waits for expiry. Acquiring/renewing also updates provider heartbeat without enabling any features.
3. **Fenced claim and reporting:** `ctf_range_worker_claim` and `ctf_range_worker_report` reject stale generations and unauthorized instance references. The old unfenced `ctf_range_claim_queued_session` and `ctf_range_report_session` permissions are revoked from the Edge `service_role`.
4. **Crash recovery:** the new holder calls `ctf_range_worker_inventory`, which adopts previously claimed running/provisioning/stopping session rows under its new generation. The trusted host must then inspect/remove the corresponding Docker project before reporting terminal status.
5. **Zero-default 24-hour launch budgets:** two operator-set limits (`max_starts_per_24h`, `max_reserved_minutes_per_24h`) default to zero. Each claim reserves a full 15 minutes and consumes its budget even if launch fails or stops early. Releasing capacity does **not** replenish spent daily reservations.
6. **Operator kill switch:** clearing `ctf_range_provider.enabled` blocks new claims and current user access while the elected worker can still reconcile and clean up sessions. Heartbeat alone never enables a disabled provider.
7. **Fail-closed local operator lock:** the CLI refuses a second worker process operating on the same Docker host. A stale lock after host/process failure requires deliberate operator inspection before removal.
8. **Regression and real database tests:** new Node tests for forgery, fenced cleanup, quota refusal, lease loss, crash recovery and process locking; disposable PostgreSQL 17 tests for ownership takeover, budget exhaustion, legacy RPC revocation and disabled-provider cleanup.

## Claim cost model — not actual money

Let `C` be total sessions **claimed** in the rolling last 24 hours, including failed or quickly terminated starts.

    next_claim_allowed = (C + 1 <= max_starts_per_24h)
                      && ((C + 1) * 15 <= max_reserved_minutes_per_24h)

This is a **worst-case reserved runtime admission rule**, not billing integration or cloud spend enforcement. It prevents the worker API from admitting more than a configured number of 15-minute launches. To guarantee a financial spending limit, we must also integrate the actual infrastructure provider's budget controls, account quotas, billing alerts, hard termination and an emergency stop policy before deployment.

Supported caps in this staging migration: at most 12 starts per 24 hours and up to 180 reserved runtime minutes per 24 hours. Defaults are zero. Actual session runtime remains capped at 15 minutes. Existing per-account daily request limits and per-user active concurrency protections remain.

## Trust and safety boundaries

- Worker lease IDs are generated by PostgreSQL and returned only through the authenticated worker Edge Function. They do not appear in browser responses, local logs, public routes or training targets.
- The edge broker accepts only a strict allowlisted `acquire`, `reconcile`, `claim`, `report`, `release` protocol and supplies its server-configured worker identity. `service_role` stays inside Supabase Edge, never in a Docker target.
- The operator CLI runs **only** with its existing explicit local Docker opt-ins, and now requires a host process lock in addition to the database fence.
- Fencing blocks stale **database reports**; it is not a guarantee against a non-cooperative process that can still manipulate the same privileged host Docker socket. The operator process lock cooperates locally, and stronger production host fencing or a microVM control plane is mandatory.
- Worker lease expires after 180 seconds. The trusted Docker command limits in this prototype are shorter but OS pause/network partitions can still cause lease loss; on loss, the process must stop rather than report a terminal state.
- No auto-cleanup daemon is deployed by this commit. On a crashed host, Docker's own application TTL prevents live HTTP service, but orphan container/network cleanup requires a restarted elected provider or an external watchdog. A stale local lock is intentionally **not** auto-deleted.
- Do not enable this prototype for multiple public users. Secure isolated sandbox hosts, distributed fencing, zero-trust ingress, and real money-denominated billing budget controls still require review.

## Deployment and test runbook

1. On a **disposable staging database**, apply the original `20261122180000_ctf_range_session_control.sql` migration and then new `20261122200000_ctf_worker_fencing_budget.sql`. Production deployment is a separate, reviewed operation.
2. Run the GitHub workflow **CTF Worker Fencing and Resource Budgets**. It starts PostgreSQL 17 with a newly generated CI password on a `--network none` container and tests the real SQL functions.
3. Run `node --test tests/ctf-range-fenced-worker.test.mjs`, `npm test`, and `npm run build`.
4. In a staging Edge deployment, configure `CTF_RANGE_PROVIDER_ID` (lowercase alphanumeric/hyphen, 3–40 characters) and the separate existing worker token. Deploy the updated `ctf-range-worker` function to staging only.
5. Enable the provider and secure ingress approval **only in reviewed staging**. Explicitly choose nonzero daily launch count/minute caps. Check that zero budgets still deny claims.
6. Start one operator worker on a private trusted machine with local Docker, the existing two execution opt-ins and `npm run range:provider -- --once` (or supervised `--loop`). The worker acquires a lease, checks inventory, handles prior cleanup and claims at most one session per tick.
7. Test live worker takeover: a second operator must be refused while the first lease is live. After an actual crash and verified stale lock recovery, a new worker must acquire a **different** UUID fence, adopt the records and reconcile actual Docker state. Stale reports must fail.
8. Test actual Docker cleanup failures: the database must NOT mark a failed cleanup as stopped and must keep the reserved capacity. Disable provider mid-run and confirm new claims stop while cleanup remains permitted.
9. Stop staging operators, remove all lab Docker projects and disable both provider/ingress flags. No public URL or billed infrastructure should exist.

## Next security gates before hosted release

1. Host-level fencing across machines, with trusted identity per dedicated sandbox worker and explicit worker-specific credentials.
2. Independent emergency watchdog for host death, stranded Docker resources and cloud shutdown.
3. Infrastructure provider hard cap / billing controls, cost unit normalization and reliable usage reconciliation.
4. Audited, browser-native TLS per-user ingress with short-lived HttpOnly sessions (or an equivalent secure authorization transport), strict origin/CSRF and revocation controls.
5. Real staging tests on hardened microVM or equivalent isolation: egress blocked, metadata inaccessible, resource limits proven, audit logging and abuse response.
