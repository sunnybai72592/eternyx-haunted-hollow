# Cybersecurity Universe — Wave 4: Relational Security Case Ledger

## Delivery and release status

This PR supplies a **staged SQL design**, an actual deployment-gated authenticated UI, read-only staging-audit SQL and security contracts. It is **not a deployed or validated migration**.

- Staged SQL: \`scripts/sql/staged-security-case-ledger.sql\`
- Read-only postdeployment audit: \`scripts/sql/read-only-security-case-ledger-audit.sql\`
- New UI: \`/cybersecurity/case-ledger\`. It reports "Schema not deployed or accessible" when the table is missing, query fails, or the user is unauthorized. The Wave 2/3 private snapshot case tools continue working.
- Existing storage, older pentest tables, and case snapshots are untouched. No direct production schema or data changes.

## Eight coordinated improvements

1. **Queryable relational assets**, with owner+engagement unique target and declared asset stewardship/criticality.
2. **Queryable relational findings** with severity, due dates, owners, remediation status, notes and indexes.
3. **Database-enforced target scope**, not just browser checks. Security-invoker triggers check current owner, attestation, lifecycle, allowed and excluded targets before asset or finding mutations.
4. **Composite ownership FKs** linking accounts, engagements, assets, findings and existing private evidence. Cross-user foreign-key laundering fails.
5. **Private evidence references**, where a finding can link only immutable metadata owned by the same account and engagement, not public URLs.
6. **Trigger-only audit history** recording status transitions and changed field names, never entire evidence content. Browser role has no history writes or record deletes.
7. **Strict privileges/RLS** on all four public tables: explicit authenticated read/insert (and selected update columns), owner-check policies, no anon grants or owner-id update privilege.
8. **Authenticated frontend ledger** with fail-closed provider detection; owner-engagement selection, scoped asset creation, findings register, retest/acceptance changes, linked evidence, and activity history. Offline checks and staging instructions included.

## Required release sequence

1. In a checkout with Supabase CLI, run \`supabase --version\`, \`supabase migration --help\`, and \`supabase migration new security_case_indexed_ledger\`. This creates the canonical filename and migration file. **Do not invent a timestamp by copying this staged proposal directly to migrations.**
2. Review the staged SQL, copy it into the generated migration, and run it **only in an isolated staging database** after the two pentest migrations.
3. Use \`supabase migration list --local\` and database advisors to confirm RLS, function execution privileges and security findings.
4. Run \`scripts/sql/read-only-security-case-ledger-audit.sql\` against staging to inspect RLS, role privileges and policies.
5. Test with two genuinely separate authenticated users, plus unauthorized (anon), using REST and SQL. Try to create assets using another owner's engagement ID; cross-owner finding/evidence IDs; scope exclusions; revoked attestations; owner reassignment; and verified/accepted statuses without retest evidence. All must fail. Confirm a real owner creates/updates a finding and only the trigger appends an audit row.
6. Regenerate Supabase TypeScript types after applying the migration, then review the generated API typing. A temporary narrow integration adapter currently permits the new tables to be queried without altering previously generated types.
7. Only after staging passes, explicitly authorize production migration and set deployment readiness. No automatic release is permitted by merging this PR.

## Known limitations and decisions

- Current remote DB connectivity is unverified; an attempted read-only \`to_regclass\` check timed out. **No production SQL was executed**.
- The schema is a proposal pending actual Postgres execution and a migration generated by the CLI. Static tests cannot replace staged RLS and relational FK verification.
- Attestation is a user statement of authorization, not a grant from a customer or system owner. No live scanning or SOC monitoring is introduced.
- No historical snapshot backfill is attempted. Older private JSON case versions remain in the evidence bucket and continue to be managed by Waves 2/3.
- Created finding history is append-only for normal app roles; privileged database administrators can still perform administrative maintenance.
