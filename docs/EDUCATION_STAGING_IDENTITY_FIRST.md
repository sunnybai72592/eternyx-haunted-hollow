## One-time synthetic fixture provisioning (after separately approved identity setup)

The new local operator script requires four distinct pre-created dedicated `rls-` Auth users: student A, student B, instructor candidate, and a separately approved staging-only operator already present in `admin_users`. It never creates Auth users or grants administrator access. The instructor must not already have a teacher record or grant. Run identity mode accounts first. Set the three existing account email environment variables, ETERNYX_EDU_FIXTURE_OPERATOR_EMAIL, ETERNYX_RLS_STAGING_REF, ETERNYX_RLS_PRODUCTION_REF, ETERNYX_RLS_STAGING_URL, ETERNYX_EDU_STAGING_DB_PASSWORD, and explicit ETERNYX_EDU_FIXTURE_APPROVAL=I_APPROVE_ONE_TIME_EDUCATION_STAGING_FIXTURES in a secure local shell. After approval, use `node scripts/staging/educationStagingSyntheticFixtures.mjs`. The wrapper pins the actual staging ref, creates a mode-0600 local recovery sentinel, and saves only the 24 fixture variable values to education-staging-fixture-variables.private.json. Never commit or upload it. The SQL transaction creates seven labeled synthetic exams, six existing attempts, two grades through the real trusted finalizer and one entirely unused fresh exam. It refuses a duplicate fixture run; no deletes or resets. The read exam expires after 24 hours. Use the full release **journey** mode, not independent rehearsal mode (the baseline final-A review is already finalized, and journey substitutes the actual new attempt). Re-run identity mode granted after provisioning. Enter the manifest variables in the protected GitHub environment. The fixture preparation is not real JWT or browser acceptance. If interrupted, inspect staging and the sentinel before attempting any further operation.

## Optional one-command account setup (local trusted operator)

After explicit authorization to create four new synthetic staging Auth users, use the supported Supabase server-side `auth.admin.createUser` API via `node scripts/staging/runEducationStagingAccountProvision.mjs`. Set the previously documented staging URL/ref, production ref and public key, the staging-only service role/secret key, three dedicated email/password pairs and ETERNYX_EDU_FIXTURE_OPERATOR_EMAIL/PASSWORD, plus ETERNYX_EDU_ACCOUNT_APPROVAL=I_APPROVE_FOUR_NEW_SYNTHETIC_EDUCATION_STAGING_AUTH_USERS in a secure local shell. All four addresses must start with rls- and all four passwords must be distinct, 16–72 characters. Do not put credentials on a command line, in a committed file, or in chat. Use only dedicated synthetic addresses. The script auto-confirms these new test identities, independently verifies each through public-key Auth and RPCs, and signs out. It creates no application privileges, including for the operator candidate; the staging owner must separately authorize and provision the operator's trusted administrator membership before the fixture script can run. The local ignored mode-0600 recovery journal contains only fixed account labels and states, no passwords or user IDs. A partial failure is deliberately not retried or cleaned up automatically. Inspect the staging Auth dashboard and recovery journal first. No production actions or paid infrastructure. See https://supabase.com/docs/reference/javascript/auth-admin-createuser.
