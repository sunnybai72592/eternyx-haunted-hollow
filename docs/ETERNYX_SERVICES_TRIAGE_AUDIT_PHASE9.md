# ETERNYX Services Phase 9 — Operator accountability, audit and workload

## Completed from merged Phase 8

After PR #427 was reported merged, the connected production Supabase project
received the reviewed service_review_planner migration using Supabase's
migration operation. Post-deployment read-only SQL verified:
- Admin review queue view exists with security_invoker=true.
- Anonymous SELECT on the view is denied.
- next_review_on / next_action_kind columns and both CHECK constraints exist.
- An authenticated database role without an authenticated user session saw

The audit-history migration introduced by **this Phase 9 PR is NOT deployed
yet**. Follow the approved review and migration workflow after merge.

## Eight connected improvements

1. **Server-authored, append-only decision history** for every new or changed
   administrator triage record. Clients cannot insert or edit log records.
2. **Before/after detail** for priority, assignment, next action and internal
   UTC review date, enabling later accountability and troubleshooting.
3. **Privacy by design:** the history records only whether private note text
   changed. It does not store another copy of the confidential note.
4. **Admin-only RLS** for history queries. The trigger function lives under
   eternyx_private and is not callable by clients. Existing customer RLS
   remains unchanged.
5. **On-demand decision timeline** embedded in triage, with 20-event pages,
   stable timestamp+id pagination, verified administrator access and
   account-switch isolation.
6. **Immediate audit refresh** after a confirmed triage save; save also
   re-verifies administrator permission before committing an update.
7. **Real internal workload summary** with overdue/today/upcoming/unscheduled
   counts queried using exact PostgREST database counts. Unavailable counts
   are shown as unavailable, never as invented zeros.
8. **Actionable queue drill-down** using summary-card filters. Administrators
   can also clear a planned follow-up explicitly, then save (which is audited).

- Preserve existing triage and request ownership RLS. Do not grant INSERT,
  UPDATE or DELETE on the audit table to authenticated users.

  Existing historical triage edits are NOT fabricated or backfilled.
- Version numbers generated by prior Supabase management operations differ
  from the SQL file timestamps. Reconcile through the officially supported
  migration-repair process before future supabase db push. Do not hand-edit
  the migration history table.

## Required staging tests

- Admin A creates triage: one 'created' decision is written with actor A,
  priority and assignment. Another admin may view it through RLS.
- Admin B changes priority, scheduled date and internal note: one 'updated'
  decision appears with old/new metadata and note_changed=true but no note
  contents in the audit table.
- Save without actual field changes: no duplicate audit event.
- Anonymous and customer accounts cannot SELECT audit records or the
  administrator review queue; only active verified administrators may view
  the history and workload.
- Customer A / customer B requests remain isolated across sign-in/out.
- Submit 25 triage updates and verify the history's Load older page works.
  Two admins editing concurrently must still respect updated_at optimistic
  locking on the underlying triage table.
- Count cards show the exact actual number of rows in each UTC due bucket,
  then refresh accurately after a date or assignment changes.
- Verify mobile, desktop, keyboard, reduced motion and full GitHub CI.

## What this does not do

This phase makes no billing decisions, contract promises, response SLAs,
automated customer messages, automatic work execution or testing authorization.
The due buckets reflect admin-entered internal review targets only.
